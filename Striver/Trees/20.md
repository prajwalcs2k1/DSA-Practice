The tricky part of this problem is:

* Width is measured using the **position indexes as if the tree were complete**
* Null gaps between nodes also count

Example:

```text
        1
       / \
      2   3
     /     \
    4       7
```

At the last level:

```text
4 null null 7
```

Width = `4`

But your idea based on left/right horizontal distance would not capture these internal gaps.

---

## Why `pow(2, minValue)` fails

Suppose:

* left horizontal distance = -2
* right horizontal distance = +2

Then:

```js
min(abs(-2), abs(2)) = 2
pow(2,2) = 4
```

But width is not always `2^level`.

Consider sparse trees:

```text
        1
       / \
      2   3
       \    \
        5    9
```

Positions:

```text
2 -> index 2
3 -> index 3
5 -> index 5
9 -> index 7
```

Width at last level:

```text
7 - 5 + 1 = 3
```

Your formula cannot derive this.

---

## Correct intuition

The standard solution uses:

* BFS level order traversal
* Assign indexes like a complete binary tree

If a node has index `i`:

* left child → `2*i`
* right child → `2*i + 1`

Then for each level:

```text
width = lastIndex - firstIndex + 1
```

---

## Visualization

```text
            1(1)
          /      \
       2(2)      3(3)
      /            \
   4(4)            7(7)
```

Last level width:

```text
7 - 4 + 1 = 4
```

---

## Core formula

\text{Width} = \text{lastIndex} - \text{firstIndex} + 1

---

## Time Complexity

* BFS traversal → `O(n)`
* Space → `O(n)`

---

## Common interview insight

This problem is basically:

> “Measure width including null gaps”

That is why simple horizontal distance or node count per level is insufficient.

---

## 🔴 Important Detail: Index Normalization (Overflow Handling)

While assigning indices using the complete binary tree logic:

* left → `2*i`
* right → `2*i + 1`

the index values can grow **exponentially with depth**.

---

### ⚠️ What can go wrong?

In deep or skewed trees:

```text
Level 0 → index 1  
Level 1 → index 2, 3  
Level 2 → index 4, 7  
Level 3 → index 8, 15  
...
```

👉 Indices grow roughly like **O(2^depth)**

Even with `long long`, this can lead to:

* **Integer overflow**
* Negative or incorrect values
* Wrong width calculation

---

### ✅ Solution: Normalization

At every level, we subtract the **minimum index of that level**:

```cpp
index = index - minIndex;
```

---

### 🧠 Why normalization works

Width is calculated as:

```text
lastIndex - firstIndex + 1
```

If we subtract the same value from all indices:

```text
(last - min) - (first - min) + 1 = last - first + 1
```

👉 Width remains unchanged

---

### 🎯 Benefits of Normalization

* Keeps index values **small and manageable**
* Prevents **overflow in deep trees**
* Ensures correctness even for large inputs
* Maintains **relative positioning**, which is all we need

---

### ❌ If NOT handled

* Code may pass small test cases but fail on large/deep trees
* Overflow leads to **incorrect width values**
* Can produce **negative or undefined results**

---

## 🔥 Final Insight

> We don’t care about absolute indices — only **relative distance within a level matters**.

So we “reset” the indexing at every level to keep computations safe and accurate.
